# API client treats HTTP 200 response shorter than Content-Length as complete

**Official challenge issue:** [FinanceFlash/unvibecode#666](https://github.com/FinanceFlash/unvibecode/issues/666)

## 1. Problem summary

The UnvibeCode 0.4.0 API client's download loop treats EOF as completion without checking the received byte count against the response's declared `Content-Length`. In the controlled reproduction, a short HTTP 200 response proceeds to ZIP extraction; `zipfile.BadZipFile` then escapes the CLI's normal error handler and terminates the process with exit code 1.

The primary defect reported here is failure to validate download completeness. The uncaught ZIP exception is the downstream consequence. This report does not establish that the hosted service routinely sends truncated responses.

## 5. Expected behavior

The client should not treat a response that ends before its declared length as a complete result download. It should reject the incomplete response before ZIP extraction and report a controlled download/integrity error.

The CLI should handle an invalid or incomplete result archive without an uncaught traceback. Where the job ID is still available, the error path should retain or display the documented recovery guidance. A valid result ZIP should continue to complete normally.

## 6. Actual behavior

The mock sent an HTTP 200 response declaring 256 bytes but wrote only 11 bytes before closing the sending side. In each of the three repeated truncated cases, the CLI proceeded to ZIP extraction and exited with code 1 with an uncaught `zipfile.BadZipFile: File is not a zip file`. The valid ZIP control sent 175 bytes and exited with code 0.

| Case | HTTP status | Declared Content-Length | Bytes written by mock handler | CLI exit |
|---|---:|---:|---:|---:|
| Incomplete 1 | 200 | 256 | 11 | 1 |
| Incomplete 2 | 200 | 256 | 11 | 1 |
| Incomplete 3 | 200 | 256 | 11 | 1 |
| Valid ZIP control | 200 | 175 | 175 | 0 |

For each incomplete response, the mock sent 245 fewer bytes than declared. These byte counts describe the response length declared and the number of bytes written by the mock handler. The archived probe does not record the number of bytes returned by the client's `HTTPResponse.read`; no direct client-read byte count is claimed.

## 8. Impact and scope

When a result download ends prematurely in this manner, the CLI can fail with an uncaught traceback instead of reporting a controlled download error. This also bypasses the normal recovery guidance in the handled-error path.

The reproduction establishes the client-side failure for the tested response shape. It does not establish how often such responses occur in production, whether the hosted service emits them, or whether any job result is permanently lost.

## 9. Related issues and duplicate check

- [Issue #643](https://github.com/FinanceFlash/unvibecode/issues/643) discusses interrupted reads that raise a URL/network error and can leave a partial destination file. That is related to incomplete downloads, but it describes a different failure path. This report reproduces a response that ends at EOF without a read-time transport exception: the client accepts the short body as complete, then the CLI attempts ZIP extraction and raises an uncaught `BadZipFile`.
- [Issue #775](https://github.com/FinanceFlash/unvibecode/issues/775) overlaps with this report in the downstream symptom: a corrupted/truncated archive can lead to `BadZipFile`. This overlap is genuine. The narrower trigger isolated here is upstream of archive parsing: the client download loop treats EOF as completion without validating the received byte count against a declared `Content-Length`. The controlled test sends HTTP 200 with `Content-Length: 256` but writes only 11 bytes, then verifies that the CLI proceeds to ZIP extraction and fails. The valid-ZIP control succeeds.

The distinction claimed here is the specific HTTP response-completeness failure and its source-level location, not the `BadZipFile` symptom by itself. The archived probe/log demonstrate the repeated CLI failure and valid-ZIP control; they do not contain a client-read byte counter. Whether maintainers consider the narrower trigger sufficiently distinct from #775 is ultimately for them to decide. This report makes the overlap explicit.

## 10. Suspected cause and suggested fix

The reproduced behavior and inspected client path indicate that the download loop treats EOF as completion without validating the received byte count against the declared `Content-Length`.

Suggested improvements:
1. Validate response completeness before treating the download as successful. When `Content-Length` is present, compare it with the number of bytes actually received; also handle premature termination when the length is absent or transfer framing indicates an incomplete response.
2. Treat incomplete downloads as download errors and do not pass them to ZIP extraction.
3. Handle `zipfile.BadZipFile` in the CLI's controlled error path as a defensive fallback.
4. Preserve and display available job recovery information when the result download fails.

These are defensive recommendations. Maintainers should confirm the precise implementation root cause against the released 0.4.0 source.
